# Gemma 4 field-work chain: local result

Date: 2026-09-29. Machine: Apple M4, 16 GB unified memory. Model: `mlx-community/gemma-4-12b-it-4bit` revision `73bcf09092aa277861d5a191b989b666f7f32e8f`; the two weight shard hashes are pinned in `verify_model_replay.py`. The experiment uses four local processes with independently generated Ed25519 validator keys. They verify in sequence to fit memory on this one machine.

The post-fix run finalized two predecessor-linked blocks. Every node independently checked the field witness, replayed the pinned Gemma inference, ran the NAOME proof checker, and signed each block. Each block collected four valid votes against a quorum of three. A separate full replay accepted the two-block chain and reproduced its final tip. The run rejected a prior finalized block and a valid alternate successor at the finalized tip. Negative vectors rejected modified signatures, a missing quorum, changed predecessor or block hash, and nine modified work inputs or commitments. Three focused reference tests passed.

The exact run output, generated receipts, witnesses, proofs, blocks, signatures, and per-node ledgers are under `.local/gemma4-chain-final`. The run writes validator private keys there for local inspection; they are disposable test keys. To reproduce, follow `USAGE.txt` from the repository root. Both prompts provide the applicable proof rules; the second also states the derivation order, so its accepted result is a plumbing test rather than evidence of autonomous proof discovery.

This is a functional local research chain, not a security claim for Proof of Useful Work. The challenge-derived rank-one finite-field encoding and full intermediate transcript are independently recomputed, but this workload does not establish the paper's hardness assumption. An exact shortcut exists for the earlier static-prompt variant. Challenge bytes now enter the actual Gemma prompt and change its first projection activation, but a later row-cache counterexample also reconstructs a new challenge transcript with almost all ordinary input rows reused. Verification costs more than the work being checked because every node replays the full model. There is no calibrated difficulty, secure fork choice, open validator admission, anti-Sybil mechanism, or physical multi-machine result. The two proof templates are fixed; the run does not demonstrate new research discovery.

## Paper check and validator optimization (2026-09-29)

Evidence baseline: merged code `86c47c18e2d41c5779b4231a2a8c40a6c253f6f8`; [Komargodski and Weinstein, *Proofs of Useful Work from Arbitrary Matrix Multiplication*, arXiv:2504.09971v4](https://arxiv.org/html/2504.09971v4), dated 2025-11-13, PDF SHA-256 `9ace5d5ffe56fc5af8d11f3380ce94e766daaf8ca07a93adca69aa73c77c508a`. The same work is indexed as IACR ePrint 2025/685. The measured inputs are the unchanged `.local/gemma4-chain-final` artifacts: genesis SHA-256 `0276a4ef8dd2343d26aaa94922c01b4f523ffc9632a4c003dd98bc535b8fd0bb`, block JSON hashes `a140868c4659c5614e25a3393b3a3d473a9d81da5efdbf5f8afeb463332ce136` and `8fb54f32e65d5f654d41c735891d4c999fa2fbba678ae7ecbe9ceeffa557861f`. The optimization leaves those acceptance rules and limitations intact. Before changes, block-2 CPU field verification took 2.316, 2.306, and 2.308 seconds on this M4; `cProfile` attributed about 2.074 seconds to two integer matrix products. A full block-2 validator replay took 19.861 seconds without first-block weight hashing, including two field checks of about 2.61 and 2.41 seconds and a 14.83-second Gemma subprocess. A first-weight-check replay took 22.364 seconds, including 2.95 seconds hashing model shards.

The optimized `chain_demo` removes one duplicate full field check; `verify_model_replay` still performs it before Gemma replay. `field_verify.product` uses binary64 BLAS for each encoded chunk, converts the exact integer result back to int64, and reduces modulo the field. For the fixed K=3840 and q≤65521, even the largest possible unreduced dot product is below 2^53, so every integer multiplication and accumulation is exactly representable in binary64; an explicit range and bound guard enforces this. On the same saved block-2 witness, full CPU field verification took 0.458, 0.435, and 0.430 seconds and all original transcript hashes matched. A slow int64 reference test covers random entries and the maximal field value over the full K width.

Replay no longer compresses a second, unused NPZ witness. The original block witness is still loaded and checked, while the replay still computes the projection, compares token IDs, model/input/weight/scale hashes, field commitments and proof bytes, and reruns the proof checker. Compressing the 12.7-MB uncompressed block-2 arrays alone cost about 0.50 seconds in three local trials. A four-process saved-chain replay after all changes measured block 1 at **15.421, 15.277, 15.463, 15.694 seconds** and block 2 at **14.705, 14.512, 15.023, 14.615 seconds** per validator. A second run on the final source measured block 1 at 15.422, 15.202, 15.437, 15.483 seconds and block 2 at 14.531, 15.352, 14.649, 14.411 seconds. The original two-block run measured block 1 at 19.433–19.619 seconds and block 2 at 19.023–19.219 seconds. This is a roughly 4-second local reduction per validator, with run-to-run variation; it is not a cross-hardware performance claim.

All four fresh validator processes reproduced both saved vote signatures and identical two-entry ledgers, and rejected a replayed finalized block. The nine receipt tampering vectors, six chain vectors (including two altered work artifacts with rebound block hashes), and four focused reference tests pass. A persistent warm model per validator was rejected for this machine: four independently held ~7.2-GB models exceed 16 GB, and a shared replay service would remove process independence. Sharing one validator's model-weight hash result with the others was rejected because each process must check its own pinned weight files. Skipping full Gemma replay or the field transcript would change the accepted evidence and was not used. A paper-conformant instantiation would require a separate protocol and security-design scope, including challenge selection, tiled transcript distribution, difficulty, and a cheaper verifier.

The row-cache check uses the saved block-2 receipt SHA-256 `c99f09878ec95182d349c26f1df0938fb01fe0ba4062d20d4adfb604b51d5e5d` and alternate-successor receipt SHA-256 `b44495b77b5f95903954b5d963015b07dfbfae00c7461ad3cc611a133a591543`. Their predecessor and question template agree while the nonces differ. For each field, `shortcut_demo.py` cached the ordinary `A·B` partials of block 2, reused 393 matching rows, computed partials for six new rows, and applied the rank-one cross terms to reproduce the alternate transcript hash exactly. On this M4, the shortcut's full transcript materialization took about 0.25 seconds per field versus about 0.11 seconds for the optimized direct CPU encoded product, so these measurements do **not** show a practical speed advantage. They do show that prompt binding alone does not force a fresh full encoded GEMM in this instance. No security reduction from the paper's square tiled scheme to this rectangular scheme is known here.
