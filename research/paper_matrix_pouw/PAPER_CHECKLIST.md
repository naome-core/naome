# Pinned paper implementation checklist

Source: Komargodski and Weinstein, [arXiv:2504.09971v4](https://arxiv.org/pdf/2504.09971v4), §§2, 5, 6.1–6.5. This checklist records the paper's requirements and separates executable algebra from protocol choices the paper leaves open. It does not claim the paper's hardness conjecture is proven.

| Clause | Required behavior | Status in this research path |
| --- | --- | --- |
| §6 opening | Inputs and output are square `n×n` matrices over a finite field `F_q`. | Implemented as parameterized prime `q<2^64`, positive `n`, and divisor `1≤r≤n`; no production parameter set chosen. |
| §6.1, Algorithm 6.1 | `MatMul_r` uses `r×r` tiles and retains every cumulative tile after each inner tile product, indexed by `(i,j,ℓ)`. | Implemented with exact field arithmetic and complete transcript. |
| §6.2, Definition 6.2 | Decode always returns `A·B`; transcript unpredictability is a computational condition. | Completeness tested against an independent scalar product; unpredictability cannot be established by functional tests. |
| §6.3, Algorithm 6.2 | Solve encodes, computes the full `MatMul_r` transcript and product, decodes, and returns `(C, π)` with `π=(A,B,z)` and `z` the transcript. Verify recomputes and compares the full transcript. | The Rust tests retain a separate literal full-transcript reference and negative vectors. This printed algorithm does **not** include a transcript hash or threshold and is **not** the selected acceptance rule. |
| §6.5, Algorithm 6.4 | Noise factors `E_L,F_L∈F_q^{n×r}` and `E_R,F_R∈F_q^{r×n}` give `E=E_L E_R`, `F=F_L F_R`; encode adds them, decode subtracts `(A F_L)F_R + E_L(E_R(B+F_L F_R))`. | Implemented with exact arithmetic. The printed Decoder signature omits `A,B` although its body uses them; the reference passes them explicitly. |
| §6.5.1, Lemma 6.5 | Independent uniform factor entries yield rank-`r` noise with the paper's small statistical error from rare rank deficiency. | Implemented entry sampling without rejection, matching the paper's stated distribution; no claim about a deployed entropy source. |
| §2 overview | Oracle derives factors from an unpredictable `σ` bound to `A,B`; `z=O(transcript)` must meet a threshold corresponding to `ε`. | **Selected acceptance interpretation.** Rust `solve`/`verify` use a typed oracle interface, recompute `z`, and enforce `z < 2^(256-d)` for a supplied `d=log₂(1/ε)`. The standalone SHA-256 oracle and canonical byte format are research candidates, not adopted consensus choices. The discrepancy with §6.3 is resolved in favor of §2; the two algorithms are not identical. Challenge source, parameter profile, and difficulty schedule remain open. |
| §5, Definition 5.1 | Verify has constant-factor lower work than Solve; prover overhead approaches zero. | Unverified for this research path. Literal §6.3 Verify repeats encoded multiplication; practical cost and the formal efficiency claim need separate evaluation. |
| §6.5, Assumption 6.4 | No asymptotically faster way to compute all intermediate values for random rank-`r` inputs. | Conjectural in the paper; functional vectors cannot validate it. |
| §7 | A native useful matrix operation can consume the exact decoded product. | Blocked for Gemma: the existing int7 rectangular projection is not native exact Gemma work. No paper-level claim or chain integration. |

The standalone `naome-pouw` Rust crate defines **research-v1** canonical bytes and a SHA-256 oracle candidate; it implements the chosen §2 hash-and-threshold rule with complete recomputation. Its test-only scalar reference independently calculates the product and every cumulative tile and checks the literal §6.3 equality rule. The fixed 2×2 arithmetic vector and pinned SHA-256 bytes are checked entirely in Rust; the byte inputs are specified below so the vectors can be reproduced without an external reference program. No Python files or execution are required by this research path. This byte format has no chain authority. A deployable protocol still needs an unpredictable challenge source, a fixed field/size/rank/security profile, difficulty and fork-choice policies, and review of the concrete oracle instantiation. The paper leaves these choices open. It also does not establish compatibility with native Gemma arithmetic or prove Assumption 6.4.

Rust research-v1 encodings are big-endian and row-major: parameters `NPMP1 || q:u64 || n:u32 || r:u32`; complete transcript `NPMT1 || parameters || cell_count:u64 || every cumulative tile element:u64` in `(i,j,ell,x,y)` order; solution `NPMS1 || parameters || A || B || C || z[32]`. Each matrix has exactly `n²` field elements. Factor expansion hashes `naome:research:pouw:factor:v1\0 || parameters || challenge[32] || A || B`, then samples four independent factors with tagged counter-mode SHA-256 and unbiased rejection. Transcript hashing uses `naome:research:pouw:transcript:v1\0 || complete_encoded_transcript`. These domains and bytes are reference vectors, not a selected network profile. The challenge is supplied by the caller; the crate does not establish its freshness.

The Rust verifier fully recomputes the factors, all tiles, the decoded exact product and `z`, then tests `z < 2^(256-d)` for caller-supplied difficulty bits `d`. It does not provide the cheaper SNARK verifier sketched in §2 Remark 2.2. The SHA-256 instantiation heuristically replaces the ideal random oracle; neither its security nor the paper's Assumption 6.4 follows from passing vectors. The user chose §2 acceptance over the inconsistent literal §6.3 equality-only algorithm, which remains covered by the Rust test-only reference for comparison.

On the local arm64 machine, pinned Rust 1.97.1 `release`, the ignored measurement test ran ten attempts with `q=65521`, `n=128`, `r=8`, and a supplied zero-bit threshold. Median Solve was 22.595 ms and median full Verify was 22.566 ms. The test includes factor expansion, the complete transcript, decoding and hashing. This tiny in-memory reference workload is not a Gemma inference, native-usefulness, multi-node, or network-throughput measurement; near-equal costs demonstrate that the current verifier repeats the work.

Reproduce the arithmetic, fixed byte vectors, and acceptance-boundary tests from the repository root with the pinned toolchain:

```sh
cargo +1.97.1 test -p naome-pouw --profile test --all-targets --all-features --locked
```
